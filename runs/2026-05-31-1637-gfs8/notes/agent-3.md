# Agent 3 Note

## Angle

Team norms make code reviews effective by reducing delay, protecting trust, and keeping feedback focused on shared engineering goals.

## Findings

- Fast reviews usually come from explicit expectations: small PRs, clear ownership, review time targets, and reviewers who either respond promptly or hand off.
- Kind reviews focus on the code and its impact, not the author; phrasing feedback as questions, risks, or tradeoffs helps keep critique constructive.
- Teams move faster when they separate blocking issues from preferences, using labels or conventions like “blocking,” “suggestion,” and “nit.”
- Shared standards reduce repetitive debate; style guides, automated formatting, linters, and documented architectural patterns keep reviews from becoming personal taste contests.
- Healthy review culture includes appreciation and context, not just criticism: reviewers should note good decisions, and authors should explain intent, constraints, and testing.

## Evidence To Gather Next

- Review internal PR data for average review latency, number of back-and-forth comments, and PR size to identify process bottlenecks.
- Compare team review guidelines from mature engineering organizations, especially around tone, blocking criteria, and expected turnaround time.

## Open Questions

- What review response time is realistic for this team’s workload and time zones?
- Which feedback categories should be automated or documented so humans can focus on design, correctness, and maintainability?
